# SearchBench / CrateDB

[CrateDB](https://cratedb.com/) is a distributed SQL database built on Lucene.
It reaches the corpus through SQL with a `FULLTEXT` index on `body`, so the
workload runs as ordinary SQL — including the joins, which it supports natively
(unlike OpenSearch, whose nine join queries are `NULL`).

Runs `crate:6.4.1` (**Lucene 10.4.0** — the same generation as Elasticsearch 9.5
and OpenSearch 3.8, so the comparison isn't across Lucene versions). Needs
`docker`, `curl`, `jq`, and a `python3` with `requests`.

## Run

```bash
# Smoke
SEARCHBENCH_DATA_DIR=/path/to/data SEARCHBENCH_DATASET=otel_logs_1m ./benchmark.sh --index

# Full benchmark
SEARCHBENCH_DATA_DIR=/path/to/data ./benchmark.sh --index
# -> results/cratedb_otel_logs_1b.json
```

## Schema

`create_table.sql` mirrors `elastic/config/index_mapping.json` and
`serenedb/create.sql`: one shard, no replicas, 30s refresh, `best_compression`,
attribute maps stored but never indexed, and columns nothing filters on set
`INDEX OFF` (their columnstore survives, so `scope_name` still groups). CrateDB
has no equivalent of Elasticsearch's index sorting.

`body` is tokenized by a custom `char_group` analyzer — split on whitespace,
punctuation and symbols, then lowercase — which is **token-identical to ES's
`body_analyzer`** and to SereneDB's `ts_split_by_non_alpha(Body, true)`.
Deliberately not `english`: stemming and stopword removal change which rows
match, not just how fast.

`body` also keeps its **plain index** on top of the fulltext one. That is a real
extra cost versus the other engines, and it is deliberate — see below.

## Loading

serened (a throwaway container embedding DuckDB) reads the parquet corpus and
streams NDJSON into `ingest.py`, which issues concurrent bulk `INSERT`s.

CrateDB documents `COPY FROM` as its bulk-import statement, but it only accepts
a URI: `COPY FROM STDIN` is unsupported over pg-wire, and it reads nothing from
a FIFO (returns `rowcount 0`, no error). Using it would mean staging the corpus
as NDJSON first — ~9 GB gzipped at 100m, ~93 GB at 1b — purely to be read once.
Measured on this corpus, concurrent `INSERT` is also simply faster:

| method | rows/s | staging |
|---|---|---|
| bulk INSERT ×8 | **68,393** | none |
| bulk INSERT ×1 | 16,168 | none |
| COPY, 8-way parallel | 54,085 | full corpus |
| COPY, serial chunks | 28,800 | one chunk |

Throughput peaks at 8 workers; the table is one shard, so more writers only
contend. `./load` finishes with `REFRESH` and `ANALYZE` — the latter
is CrateDB's documented post-import step, without which all 92 queries are
planned with no statistics.

## Queries

`queries.sql` is generated by `translate.py` from `elastic/queries.dsl`
(Q01–Q83) and `postgres/queries.sql` (Q84–Q92, the self-joins). Validated
against Elasticsearch 9.5 on an identical 200k-row sample: **32/32 count
queries returned exactly equal totals and 9/9 `terms` aggregations produced
identical bucket sets.**

Three CrateDB behaviours forced non-obvious translations, each of which returns
a *wrong answer silently* rather than erroring:

- **`~` returns zero rows against an `INDEX OFF` column.** No error. Eight
  queries are regex-based, so `body` keeps its plain index; without it they
  would all have looked instant and empty.
- **`minimum_should_match` is ignored.** Q09/Q42 ask for "at least 2 of 4
  terms"; CrateDB returned the plain-OR count (30,112 vs ES's 17,939). They are
  expanded into an `OR` over every 2-subset, which reproduces ES exactly.
- **Java's `\b` treats `_` as a word character**, but the analyzer splits on it,
  so `\b`-anchored regexes miss tokens inside e.g. `order_id` — 350 rows adrift
  on Q17. Term-level patterns use `(?<![a-z0-9])`/`(?![a-z0-9])` instead.
